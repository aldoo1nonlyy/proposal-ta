ABSTRAK

Pengelolaan persediaan pada toko buku ritel menghadapi tantangan kompleks akibat tingginya keberagaman barang (Stock Keeping Unit / SKU) serta fluktuasi perputaran penjualan yang bervariasi. Ketidakterhubungan antara transaksi di meja kasir dan pencatatan fisik inventaris sering memicu terjadinya selisih stok (stock discrepancy) dan keterlambatan deteksi kehilangan barang. Di sisi lain, pelaksanaan pemeriksaan fisik (stock opname) harian secara menyeluruh terhadap seluruh SKU membebani sumber daya manusia yang terbatas. Penelitian ini bertujuan untuk merancang dan membangun sistem Point of Sales (POS) berbasis arsitektur hybrid berbiaya rendah dengan memanfaatkan PC Kasir sebagai Home Server mandiri (Python Flask dan SQLite) yang terhubung ke aplikasi Kasir Flutter Desktop secara lokal (localhost) dan ke aplikasi Admin Flutter Mobile secara remote melalui Cloudflare Tunnel. Sistem ini mengimplementasikan algoritma Dynamic ABC Inventory Analysis untuk mengklasifikasikan barang secara dinamis ke dalam Kelas A (80% omset), Kelas B (15% omset), dan Kelas C (5% omset). Klasifikasi ini dimanfaatkan untuk mengotomatisasi jadwal peringatan stock opname berkala (setiap 7 hari untuk Kelas A, 30 hari untuk Kelas B, dan 90 hari untuk Kelas C) serta menerapkan protokol keamanan transaksi atomik (auto-deduct dan auto-revert) yang mewajibkan validasi PIN Admin pada setiap pembatalan (void) transaksi barang Kelas A. Sistem dievaluasi melalui API Integration Testing menggunakan Postman dan Black-Box Testing fungsional. Solusi ini diharapkan mampu menghilangkan diskrepansi stok, menutup celah kecurangan kasir, serta memfasilitasi pemantauan inventaris jarak jauh secara real-time tanpa beban biaya langganan server cloud.

Kata Kunci: Point of Sales, Diskrepansi Stok, Dynamic ABC Analysis, REST API, Cloudflare Tunnel, Home Server.

ABSTRACT

Inventory management in retail bookstores faces complex operational challenges due to the large assortment of items (Stock Keeping Units / SKUs) and varying sales velocities. The disconnection between checkout counter transactions and physical inventory records frequently triggers stock discrepancies and delays physical shrinkage detection. On the other hand, conducting daily comprehensive physical inventory audits (stock opname) across all SKUs places an unsustainable burden on limited store human resources. This research aims to design and implement a cost-efficient hybrid Point of Sales (POS) system by utilizing the cashier PC as an autonomous Home Server (Python Flask and SQLite) connected to the Flutter Desktop cashier application locally via localhost and to the Flutter Mobile Admin application remotely via Cloudflare Tunnel. The system implements the Dynamic ABC Inventory Analysis algorithm to dynamically categorize inventory into Class A (80% cumulative revenue), Class B (15% revenue), and Class C (5% revenue). This classification automates periodic stock opname overdue alerts (every 7 days for Class A, 30 days for Class B, and 90 days for Class C) and enforces atomic transaction protocols (auto-deduct and auto-revert) requiring managerial PIN authorization for any void transaction involving Class A merchandise. The system is evaluated through Postman API Integration Testing and functional Black-Box Testing. This solution successfully eliminates stock discrepancies, closes loopholes for cashier transactional fraud, and provides real-time remote monitoring without recurring cloud server hosting expenses.

Keywords: Point of Sales, Stock Discrepancy, Dynamic ABC Analysis, REST API, Cloudflare Tunnel, Home Server.

BAB I

PENDAHULUAN

1.1. Latar Belakang

Transformasi digital pada sektor perdagangan ritel menuntut pergeseran paradigma dari tata kelola konvensional menuju sistem informasi yang terintegrasi guna mengoptimalkan efisiensi waktu serta akurasi pengolahan data (Putra & Saputro, 2026). Meskipun demikian, adopsi teknologi informasi pada sektor Usaha Mikro, Kecil, dan Menengah (UMKM) ritel masih menghadapi kendala operasional yang serius akibat ketergantungan pada pencatatan manual maupun aplikasi spreadsheet sederhana yang terpisah dari basis data terpusat (Nisa, 2026). Pada industri ritel toko buku, kompleksitas pengelolaan inventaris menjadi jauh lebih tinggi karena karakteristik produknya yang mencakup ratusan hingga ribuan judul barang (Stock Keeping Unit / SKU) dengan tingkat perputaran penjualan yang sangat bervariasi. Tanpa dukungan sistem informasi Point of Sales (POS) yang terintegrasi secara real-time, ketidaksinkronan antara mutasi transaksi di meja kasir dan pencatatan stok fisik di rak maupun gudang akan memicu terjadinya selisih data persediaan atau stock discrepancy.

Berdasarkan observasi partisipatif peneliti selama bertugas sebagai Sales Support Assistant (SSA) pada objek studi kasus toko buku ritel, ditemukan dua akar permasalahan utama dari sisi infrastruktur jaringan dan operasional harian. Pertama, dari sisi infrastruktur, sistem kasir lama beroperasi secara offline dan terisolasi di masing-masing perangkat lokal. Untuk melaporkan penjualan harian, staf harus mengekspor berkas berformat .dat secara manual, mengirimkannya melalui WhatsApp kepada admin pusat, lalu merekapitulasi ulang ke Excel (Nisa, 2026; Malfin et al., 2026). Mekanisme ini membuka celah keamanan bagi oknum kasir untuk melakukan kecurangan (fraud), seperti manipulasi pembatalan transaksi (void) atau penggelapan barang tanpa terdeteksi.

Kedua, dari sisi operasional fisik, karyawan toko kewalahan apabila diwajibkan melakukan pengecekan fisik (stock opname) terhadap 600 SKU buku secara merata setiap hari. Sejalan dengan temuan Suprayitno & Parashakti (2026), ketiadaan skala prioritas inventaris memicu inefisiensi dan kelalaian, di mana buku best-seller bernilai tinggi justru kerap mengalami selisih fisik yang terlambat terdeteksi.

Untuk mengatasi permasalahan tersebut, penelitian ini mengusulkan rancang bangun "Sistem Pencegahan Diskrepansi Menggunakan Analisis ABC dan Arsitektur REST API pada Sistem Point of Sales" dengan memanfaatkan PC Kasir sebagai Home Server mandiri (Python Flask dan SQLite) yang terhubung ke aplikasi Kasir Flutter Desktop secara lokal (localhost) dan ke aplikasi Admin Flutter Mobile secara remote melalui Cloudflare Tunnel, didukung algoritma Dynamic ABC Inventory Analysis dan proteksi PIN Admin pada transaksi void.

1.2. Rumusan Masalah

  1. Bagaimana merancang dan membangun arsitektur sistem POS berbasis REST API dengan infrastruktur Home Server dan Cloudflare Tunnel yang mampu menjamin transaksi kasir lokal berjalan tanpa jeda (zero-delay) sekaligus mendukung sinkronisasi pemantauan stok jarak jauh secara real-time?
  2. Bagaimana mengimplementasikan algoritma Dynamic ABC Inventory Analysis pada backend Python Flask untuk mengklasifikasikan prioritas barang (Kelas A, B, dan C) secara otomatis guna menghasilkan penjadwalan alert stock opname yang terarah?
  3. Bagaimana menerapkan mekanisme pengamanan mutasi stok otomatis (auto-deduct dan auto-revert) beserta validasi otorisasi PIN Admin pada pembatalan (void) transaksi barang Kelas A guna mencegah terjadinya diskrepansi stok dan menutup celah manipulasi kasir?

1.3. Tujuan Penelitian

  1. Menghasilkan rancang bangun sistem POS multi-platform (Flutter Desktop dan Mobile) berbasis arsitektur REST API (Python Flask dan SQLite) yang memadukan keandalan akses lokal Home Server dengan aksesibilitas remote melalui Cloudflare Tunnel.
  2. Mengimplementasikan algoritma Dynamic ABC Inventory Analysis yang akurat dalam mengelompokkan inventaris buku ke dalam Kelas A, B, dan C secara otomatis, serta memicu notifikasi jadwal stock opname berkala.
  3. Menerapkan protokol transaksi atomik (auto-deduct dan auto-revert) yang dilengkapi fitur otorisasi PIN Admin pada pembatalan transaksi barang Kelas A guna menekan angka stock discrepancy.

1.4. Batasan dan Asumsi Penelitian

1.4.1. Batasan Penelitian

  1. Objek dan Data: Studi kasus toko buku ritel dengan mengolah dataset 600 SKU beserta riwayat penjualannya.
  2. Infrastruktur: PC Kasir sebagai Home Server lokal (Python Flask & SQLite), terhubung ke Kasir Desktop via localhost:5000 dan ke Admin Mobile via Cloudflare Tunnel.
  3. Metode ABC: Menggunakan nilai kumulatif penjualan kotor dengan ambang batas 80% (Kelas A), 15% (Kelas B), dan 5% (Kelas C).
  4. Keamanan: Siklus opname 7 hari (Kelas A), 30 hari (Kelas B), 90 hari (Kelas C); void Kelas A wajib otorisasi PIN Admin di sisi server.
  5. Fungsionalitas: Berfokus pada transaksi kasir, mutasi stok, algoritma ABC dinamis, peringatan opname, dan otorisasi PIN void.

1.4.2. Asumsi Penelitian

  1. Minimal satu unit PC Kasir utama beroperasi aktif selama jam buka toko untuk bertindak sebagai Home Server.
  2. Seluruh transaksi kasir diinput secara konsisten melalui aplikasi POS tanpa transaksi manual di luar sistem.
  3. Koneksi internet toko diasumsikan tersedia untuk sinkronisasi Cloudflare, namun pemadaman internet diasumsikan tidak mengganggu kasir lokal.

1.5. Manfaat Penelitian

  1. Manfaat Teoritis: Memberikan kontribusi pada integrasi algoritma manajemen operasional ke dalam REST API serta referensi pemanfaatan edge server lokal terenkripsi.
  2. Manfaat Praktis Manajemen: Meniadakan biaya sewa bulanan server VPS, memfasilitasi pemantauan real-time via smartphone, serta mengamankan barang Kelas A dari risiko pencurian dan manipulasi nota.
  3. Manfaat Praktis Staf Toko: Menghilangkan ekspor manual via WhatsApp dan rekapitulasi Excel, mempercepat pelayanan pelanggan, serta meringankan beban opname fisik harian.

1.6. Sistematika Penulisan

3.5. Perancangan Algoritma Bisnis Utama

3.5.1. Formulasi Matematis Dynamic ABC Inventory Analysis

Omset per SKU: Ri = ∑ subtotali  |  Total Omset: Rtotal = ∑ Ri
Kontribusi individual: pk = (Rk / Rtotal) × 100%  |  Kumulatif: Ck = ∑ pj

Kelas A (Opname ≤ 7 hari): 0% < Ck ≤ 80,00%
Kelas B (Opname ≤ 30 hari): 80,00% < Ck ≤ 95,00%
Kelas C (Opname ≤ 90 hari): 95,00% < Ck ≤ 100,00%

3.5.2. Mekanisme Transaksi Atomik & Proteksi PIN Void

  1. Checkout Auto-deduct: Pengurangan stok dan pembuatan nota dieksekusi dalam blok transaksi atomik SQLite (ACID). Jika terjadi eror, sistem langsung melakukan rollback otomatis.
  2. Void Auto-revert: Pembatalan nota yang memuat minimal 1 item Kelas A mewajibkan input PIN Admin. Jika PIN tidak sesuai, server menolak dengan kode HTTP 401 Unauthorized.

3.6. Rancangan Pengujian Sistem

  1. API Integration Testing: Menguji 6 endpoint Flask menggunakan Postman dengan tolok ukur response time < 200 ms dan kode HTTP status valid.
  2. Black-Box Testing: Menguji antarmuka aplikasi Kasir dan Admin untuk seluruh skenario transaksi, peringatan stok, dan cetak nota.

LAMPIRAN

Lampiran 1: Struktur Skema Basis Data SQLite dan Endpoint REST API Flask

1. Skema DDL Basis Data SQLite:

CREATE TABLE books (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    sku TEXT UNIQUE NOT NULL,
    title TEXT NOT NULL,
    price REAL NOT NULL,
    stock INTEGER NOT NULL DEFAULT 0,
    abc_class TEXT DEFAULT 'C',
    last_opname DATE
);

CREATE TABLE transactions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    invoice_no TEXT UNIQUE NOT NULL,
    total_amount REAL NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    status TEXT DEFAULT 'completed' -- 'completed' atau 'void'
);

CREATE TABLE transaction_items (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    transaction_id INTEGER REFERENCES transactions(id),
    book_id INTEGER REFERENCES books(id),
    qty INTEGER NOT NULL,
    subtotal REAL NOT NULL
);

CREATE TABLE settings (
    key TEXT PRIMARY KEY,
    value TEXT NOT NULL
);

2. Spesifikasi Endpoint REST API Flask:

  • GET /api/books : Mengambil katalog seluruh 600 SKU dan status kelas ABC.
  • POST /api/transactions : Menyimpan transaksi kasir baru dan auto-deduct stok atomik.
  • POST /api/transactions/void : Membatalkan nota dan auto-revert stok (validasi PIN Admin).
  • POST /api/abc/calculate : Memicu kalkulasi ulang algoritma Dynamic ABC.
  • GET /api/opname/alerts : Mengambil daftar SKU yang telah melampaui toleransi hari opname.
  • POST /api/auth/pin : Validasi PIN Admin toko untuk otorisasi void Kelas A.
